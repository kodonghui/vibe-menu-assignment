screen-brief.md의 사용자 행동과 화면 범위, montage.tokens.json의 디자인 토큰이 기준입니다.
서버와 React의 기능 연동 및 브라우저 검증은 준비되어 있으며, 이 요청은 그 기능에 적용할 화면 디자인을 정하는 단계입니다.

먼저 첨부 토큰으로 공통 디자인 시스템을 시각화하고, 그 기준 위에 다음 다섯 아트보드를 만들어 주세요.

1. 공통 레이아웃과 컴포넌트
   헤더, 메뉴 목록·메뉴 등록 내비게이션, 본문 영역, 푸터.
   주요/보조/위험 버튼, 입력창, 선택창, 메뉴 카드, 주문 상태 배지, 페이지 이동, 확인 다이얼로그의 공통 규칙.
2. 메뉴 목록
   이름 검색, 하위 카테고리 필터, 기준 가격 초과 필터, 메뉴 카드, 전체 개수, 페이지 이동, 메뉴 등록 버튼.
   카드는 메뉴 이름·가격·카테고리·주문 가능 여부를 표시합니다.
3. 메뉴 상세
   이름·가격·분류·주문 상태·메뉴 번호, 목록 복귀, 수정·삭제 버튼과 삭제 확인 다이얼로그.
4. 메뉴 등록·수정 공용 폼
   이름·가격·하위 카테고리·주문 상태, 저장·취소.
   등록은 빈 입력, 수정은 기존 값이 채워진 두 상태를 보여 주세요.
5. 상태 모음
   목록 로딩, 검색 결과 없음, 메뉴 없음, 서버 연결 오류와 다시 시도, 상세 404,
   필드별 입력 오류, 저장 중·저장 실패·저장 성공, 삭제 확인·삭제 실패.

디자인 규칙:
- 색상·글자 크기·행간·자간·간격·모서리·그림자는 첨부 토큰의 이름과 값만 사용합니다.
- 색은 semantic 토큰을 우선합니다. light와 dark 값이 있으므로 공통 규칙이 두 테마에서 유지되게 합니다.
- 첫 시안은 라이트 테마를 중심으로, 주요 버튼·카드·폼의 다크 테마 대응도 보여 주세요.
- font-size를 임의로 정하지 말고 tokens.css의 타입 스타일을 대응시킵니다.
- radius도 첨부 토큰의 실제 값으로 고릅니다. 새 색·새 간격·새 모서리 값을 추측해서 추가하지 마세요.
- 화면 크기와 레이아웃 비율은 반응형 구성에 맞게 정하되 컴포넌트 내부 간격은 토큰을 사용합니다.
- 한국어 UI로 만들고, 관리자가 메뉴를 빠르게 찾고 수정할 수 있게 정보의 우선순위를 정해 주세요.
- 데스크톱과 약 390px 폭의 모바일 화면을 함께 보여 주세요.
- 키보드 포커스, 입력 라벨, 오류 설명, 충분한 대비를 포함합니다. 상태를 색만으로 구분하지 마세요.
- 사진 없이도 완성된 카드가 되게 하세요. 실제 API에는 이미지·별점·재고·매출·주문 내역이 없습니다.
- 로그인·장바구니·결제 등 첨부 범위 밖의 기능을 추가하지 마세요.
- 저장·삭제의 대기와 실패를 사용자가 알아보고 회복할 수 있게 보여 주세요.

API와 행동의 중요한 조건:
- 가격 필터는 "입력 가격을 초과하는 메뉴"입니다. 최소/이하 가격으로 바꾸지 마세요.
- 이름 검색과 카테고리 필터는 이미 React에서 처리합니다. 새 API를 가정하지 마세요.
- 메뉴 상세 주소는 /menus/:menuCode, 등록은 /menus/new, 수정은 /menus/:menuCode/edit입니다.
- 주문 상태는 내부적으로 Y/N이지만 화면에는 주문 가능/주문 불가로 표시합니다.
- 저장 성공 후 상세 화면, 삭제 성공 후 목록으로 이동합니다.
- 삭제 전 메뉴 이름을 포함한 확인 단계와 취소를 제공합니다.
- 화면의 프로토타입용 예시 데이터는 디자인 샘플로만 쓰고 실제 서버 연동 완료로 표현하지 마세요.

마지막에 구현 담당자에게 전달할 자료를 정리해 주세요.
- 화면별 레이아웃과 공통 컴포넌트/상태 명세.
- 각 컴포넌트가 사용한 색·타입·간격·radius 토큰의 정확한 이름.
- 데스크톱↔모바일에서 바뀌는 배치와 고정되는 공통 규칙.
- 제공 도구가 지원하면 편집 가능한 HTML/CSS 또는 디자인 원본을 함께 내보내 주세요.
- 원본 내보내기가 어려우면 아트보드와 위 명세를 전달해 주세요. 실제 앱 코드는 React JS/JSX + CSS Module이며 UI 라이브러리와 CSS 프레임워크를 사용하지 않습니다.
